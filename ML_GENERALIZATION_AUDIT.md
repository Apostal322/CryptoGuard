# ML generalization audit (Phase 11.1)

Audit of the experimental phishing-transaction classifier from Phase 11 (`ML.md`). Offline
only: no Ethereum RPC request was made in this phase. Every number below comes from
`ML_AUDIT_TABLES.md` (generated by `cryptoguard ml audit`), the frozen baseline record
`docs/ml/baseline-phase11.json`, or a command named next to it. Not an independent review.

**Decision: research-only, and independent data required** (outcomes B and D of the
assignment). The model and its evaluation are technically valid and reproducible, but its
benchmark cannot establish generalization to CryptoGuard's use case, and its measured false-
positive rate makes it unusable for warnings at realistic base rates. The API no longer
scores with it; production findings were never affected.

## 1. Objective

Establish what the Phase 11 result (test AP 0.999, recall 0.977, false-positive rate 0.163)
does and does not show, fix defects that affect correctness or safety, and define the data
needed for a defensible next experiment.

**Scope of byte-level reproducibility:** verified only on one machine (Windows 11, the versions
above, 4 cores). LightGBM's `deterministic=True` makes results repeatable for the same data,
parameters, thread count and library build; it does not promise identical trees or bytes across
LightGBM versions, operating systems or CPU architectures, and joblib pickles also embed
library internals. Metric-level reproducibility is the claim; byte-level is a same-environment
observation. The registry now refuses a model whose training recorded a different major.minor
LightGBM or scikit-learn version.

**Defect found here (P2):** the dataset manifest's hash also covered the cumulative RPC request
count, so it changed without the data changing. Runs are now keyed on the table and split
hashes (`ml/cli.py`).

## 3. Dataset construction and label provenance

From the PTXPhish paper (Chen et al., NDSS 2025):

- **Phishing** transactions started from 101 public reports (social media, security blogs)
  collected over three months, then were expanded by sampling up to 50 more transactions per
  scammer address. Two security experts reviewed each and kept consensus labels; no
  agreement statistic is reported. Labels are hindsight-based (after the reports).
- **Benign** transactions come from about 60 accounts: the top 50 DeBank "Key Opinion
  Leaders" and the top 10 DeFi protocol developers, with up to 200 transactions each.
- Many "phishing" rows are the **attacker's** transactions (for ice phishing, the
  `transferFrom` that drains the victim), not victim-signed ones.

The target is therefore "is this transaction part of a known phishing operation, as opposed to
a prominent account's activity" — not "is the payment I am about to make going to a scammer".

Sample accounting (distinct quantities, not to be conflated):

| Stage | Count |
|---|---|
| Labelled hashes in PTXPhish | 18,555 (4,998 phishing, 13,557 benign) |
| Deterministic sample drawn | 2,701 |
| Collected with chain data | 2,527 (174 not reached under the request cap) |
| Valid feature rows | 2,527 |
| Outside the study window (all benign) | 791 |
| Purged: shared an account with an earlier split | 199 validation, 176 test |
| Train / validation / test | 1,041 / 148 / 172 |

Parsing re-checked: one sheet; 13 subtype columns plus "Source" columns; all 18,555 values
are valid 32-byte hashes, unique, and in exactly one category. A hash appearing in two
categories (in any letter case) is rejected (`test_a_hash_in_two_categories_is_refused`).
Poison-Hunter and Forta remain auxiliary (data card only): address-level labels, a
popularity-selected benign class, a column-shifted sample file, and Etherscan-derived labels
shared between them. Adding them would add rows, not independent evidence.

## 4. Holdout integrity

From the run ledger and git history (times UTC):

| Time | Event | Test split viewed |
|---|---|---|
| 29 Oct 05:07 | Dry run on partial data, uncommitted code; gate failed | yes |
| 05:13 | `aee2bf4`: promotion gate redesigned, selection switched to log loss | — |
| 05:14 | Full-data run with the degree-based hub rule | yes |
| 05:48 | `e9b49f1`: hub rule replaced (after a synthetic leakage test) | — |
| 05:53 | Final run `055343Z` | yes |

The study window was fixed before any training, from class block ranges (no outcomes). The
promotion criteria and model-selection metric changed after a run whose test results had been
displayed; the hub rule changed after a second one. The feature set did not change after any
test result was seen (the dry run used uncommitted code, so this rests on the session record,
not on git). The gate itself also uses the test split.

**Conclusion:** the test split is a **previously examined development benchmark**, not an
untouched holdout. No untouched holdout exists among the collected data. The 2,527 rows cannot
be reshuffled into one, and the uncollected PTXPhish hashes would not be one either: they come
from the same ~60 benign accounts and the same expanded scammer addresses, so after the account
purge few would remain, and those would share the dataset's construction.

## 5. Entity leakage

The account purge holds: on the real splits, no non-hub account appears in two splits (checked
directly), and synthetic scenarios cover a shared attacker signer, a shared lookalike
recipient, a public token, mixed-case addresses and a high-degree drainer contract
(`tests/unit/test_ml_pipeline.py`).

| Hub policy | Validation benign/phishing | Test benign/phishing | Test AP | Test FPR |
|---|---|---|---|---|
| Registry (used) | 32/116 | 43/129 | 0.999 | 0.163 |
| Degree rule (replaced) | 14/117 | 37/128 | 0.999 | 0.162 |
| No exemptions | 13/61 | 26/54 | 1.000 | 0.000 |

The registry (15 public contracts: major tokens, routers, marketplaces, Permit2) was compiled
after seeing a diagnostic list of bridging accounts that showed label counts. Every entry is a
well-known contract identifiable by name, and exempting fewer accounts only removes rows. The
policy does not move the headline metrics; it changes how many rows are left to measure on.

Residual dependence: the purge separates splits, not rows within a split. The 43 benign test
rows come from **12 senders** (11 account clusters); 129 phishing rows from 93 senders. No
feature vector in validation or test is identical to one in training.

## 6. Temporal validity and observation boundary

Feature lineage: every feature comes from the transaction, its receipt, or state read at
block − 1 (sender nonce, target code). Block number and time are never features. Missing
historical state fails the collection (an error, retried), never a zero. A receipt missing
for a mined transaction used to be scored as "no logs, failed"; it is now `incomplete` and
never scored (fixed, tested).

The boundary is **post-inclusion**: the receipt is part of the input. The model cannot be used
before signing without transaction simulation. Same-block effects: the nonce and code are read
at the previous block, so a contract deployed earlier in the same block reads as "no code" (a
conservative choice, documented).

## 7. Selection bias and shortcuts

Inside the study window (`ML_AUDIT_TABLES.md` §8):

| Property | Benign | Phishing |
|---|---|---|
| `transferFrom` calls | 1 of 265 | 445 of 1,106 |
| `approve` calls | 25 | 0 |
| EIP-1559 fee fields present | 95.5% | 66.7% |
| Median prior transactions of the sender | 306 | 74 |
| Target has 4+ vanity zero nibbles | 4.2% | 17.8% |

Fixed-hyperparameter experiments (no per-subset tuning), test = development benchmark:

| Features | Test ROC-AUC (LightGBM) | Test ROC-AUC (logistic) |
|---|---|---|
| All 37 | 0.995 | 0.951 |
| Function family only (10) | 0.870 | 0.870 |
| Transaction type only (4: fee format, creation, zero value, calldata size) | 0.875 | 0.758 |
| Sender history only (1) | 0.458 | 0.806 |
| All except shortcut groups (21) | 0.965 | 0.779 |

How a transaction was *sent* (fee format, function family, sender history) separates the
classes almost as well as anything else: attacker tooling versus prominent humans. Removing
those groups still leaves LightGBM at ROC-AUC 0.965 from log structure and contract
properties, so not everything is a shortcut. None of this shows that the model would recognise
phishing against ordinary users, who are absent from the benign class.

## 8. Statistical uncertainty

| Quantity | Estimate | Wilson 95% (rows independent) | Cluster bootstrap 95% |
|---|---|---|---|
| Recall | 126/129 = 0.977 | 0.934 to 0.992 | 0.933 to 1.000 |
| False-positive rate | 7/43 = 0.163 | 0.081 to 0.300 | 0.043 to 0.364 |
| Precision | 126/133 = 0.947 | 0.895 to 0.974 | — |
| AP | 0.999 | — | 0.994 to 1.000 |

The cluster bootstrap resamples account components, the honest unit here. Training-time
intervals now do the same (`train.bootstrap_ci(..., clusters=...)`); Phase 11's row bootstrap
understated the uncertainty. AP must be read against the test prevalence of 0.75: AP above
prevalence is 0.249. To bound the false-positive rate below 1% at 95% confidence with zero
observed false positives requires 299 independent benign rows; below 0.1%, 2,995. With 43
rows from 12 senders, one more false positive moves the rate by 2.3 points.

## 9. Real-world base rates (arithmetic, not measurement)

Per 10,000 transactions, using recall 0.977 and false-positive rate 0.163:

| Assumed phishing prevalence | True alerts | False alerts | Precision |
|---|---|---|---|
| 0.01% | 1.0 | 1,628 | 0.001 |
| 0.1% | 9.8 | 1,626 | 0.006 |
| 1% | 97.7 | 1,612 | 0.057 |
| 5% | 488 | 1,547 | 0.240 |

Even at 5% prevalence, three alerts in four would be false. The model is not suitable for
automated security warnings.

## 10. Errors (development benchmark)

Confirmed from the stored model: 7 false positives and 3 false negatives. Five of the seven
false positives and two of the three misses are single `transfer()` calls with one Transfer
log and no ETH value; two false positives call vanity-mined contracts (10 and 14 zero nibbles);
one miss is a fake-token transfer whose receipt has no logs. These are hypotheses for the next
experiment, not tuning targets: nothing was changed in response to them.

## 11. Wallet-history features

`ml/history.py` implements point-in-time features for a payment from the paying wallet's own
history: prior payments and interactions with the recipient, time since first and last
interaction, distinct prior recipients, share of recent payments to new recipients, whether the
recipient imitates a counterparty the wallet chose (reusing the poisoning detector's
`is_lookalike`), unsolicited events with the recipient, and observed lookalike plantings
(including spoofed outgoing transfers). Data contract: explicit coverage, two boundaries
(pre-signing, pre-execution), `None` for unknown with indicator columns in the model row, and
reverted payments counted as choices but not payments. 13 tests cover empty, partial and
missing history, reverted and unknown receipts, same-block ordering, casing, and metamorphic
properties (future events and reordering change nothing).

**No accuracy claim:** PTXPhish has no wallet histories, CryptoGuard's replay fixtures have
histories but only 4 labelled incidents, and no RPC budget was available to fetch histories.
The infrastructure is ready for the next dataset (§16).

## 12. Calibration

Scores are bimodal: on validation, 30 of 32 benign rows score below 0.2 and 116 rows score
above 0.8; on test, all eight rows between 0.2 and 0.8 are benign. Training data were 82%
phishing, so even a calibrated score would describe that mix, not real traffic. With 32 benign
validation rows from 5 senders, no calibrator can be fitted reliably, and none was. The API,
the CLI and the model card now state that the score is an **uncalibrated ranking score**.

## 13. Registry and inference security

Defects fixed:

- **P1: wrong chain could be scored.** The scoring route read through the provider's raw client
  and skipped `verify_chain()`; it now verifies the chain and refuses anything but mainnet,
  where the model was trained.
- **P1: missing receipt scored as a failed transaction** (§6).
- **P1: the API scored with a model that had no untouched-holdout evidence.** Approval levels
  now separate `research_only` (gate passed on a development benchmark; CLI scoring only) from
  `shadow_approved` (requires an untouched, once-evaluated holdout recorded in the model card);
  the API requires the latter.
- **P2: registry trusted a path from `registry.json`.** Runs are now addressed by a validated
  run id inside the runs directory; model cards are schema-checked; files over 50 MB are
  refused; library versions must match.
- **P2: pickle for LightGBM.** New runs store LightGBM's text format (no pickle). On the 320
  real validation and test rows, the baseline model's text form and its pickle gave identical
  scores (maximum absolute difference 0.0, `docs/ml/baseline-phase11.json`). Other model
  families still use a hash-checked pickle.
- **P2: unbounded scoring.** One scoring at a time per event loop, 30 s overall timeout.

A hash check proves a file matches its card; it does not make a card trustworthy. The trust
boundary is the local `data/ml` directory.

## 14. Collector and request budget

**P1: the budget could be exceeded or lost.** Phase 11 counted attempts after the fact and
stopped at a margin; a killed session lost its count (charged later by estimate), and two
collectors could each spend the full remainder. Now every HTTP attempt, retries included,
reserves one unit in a durable ledger first (`RequestLedger`, `BudgetedTransport`): exclusive
lock file, atomic replace, fail-closed on a corrupt ledger. A crash after reserving over-counts;
nothing can under-count. 11 tests with counting mock transports cover the cap, retries, a crash
mid-run, two concurrent collectors, five threads racing (this found a Windows lock bug, fixed),
a corrupt ledger, a cut-off checkpoint line (repaired and re-fetched), a corrupt middle line, a
missing receipt and duplicate records. The ledger reads 11,953 of 12,000; the authorization is
treated as exhausted.

## 15. Monitoring

PSI uses per-bin training shares (ties handled). The drift report now also gives scoring
outcomes, schema mismatches, unreadable lines, latency and score distribution, reads only the
last 10,000 entries, and states that unlabelled drift cannot show accuracy loss.

## 16. Required next dataset

To measure what CryptoGuard needs — whether an outgoing payment from an ordinary wallet goes
to a poisoned lookalike — the next dataset must have:

- **Unit:** outgoing payments (token transfers and ETH sends) from ordinary wallets, each with
  the wallet's history up to the payment.
- **Positives:** payments to address-poisoning lookalikes confirmed by an independent source
  (incident reports or a labelled list), ideally several hundred across many attackers.
- **Negatives:** at least 300 payments, from at least 100 distinct ordinary wallets (not
  prominent accounts), drawn at random from the same period, for a 1% false-positive bound.
- **Independence:** split by wallet and attacker infrastructure and by time; holdout frozen
  before any model sees it, evaluated once.
- **Sources:** the 4 replay incidents and 9 background wallets as a seed; Poison-Hunter's
  phishing addresses as candidate positives (address labels only: payments to them still need
  confirming); random wallets sampled from blocks. Licensing: Poison-Hunter has no license,
  so its addresses can be used locally but not redistributed.
- **Cost estimate:** the 13 recorded replay fixtures cost 443 to 1,361 requests each for a
  21,600-block (about three-day) history window on the free endpoint, with retries included.
  At that rate, 100 negative wallets plus 50 positive incidents is roughly 70,000 to 200,000
  requests for three-day windows, more for longer histories: a new, explicit budget decision,
  well beyond the exhausted 12,000.

## 17. Recommended next experiment

Wallet-history features against a simple history rule ("recipient imitates a past counterparty
and was never paid") on the dataset above, with the holdout frozen first. The single question:
does a learned model beat the rule CryptoGuard already applies, on ordinary wallets?

## 18. Remaining limitations

- No untouched holdout; one labelled source; a benign class of about 60 prominent accounts.
- Post-inclusion only; no simulation-based pre-signing scoring.
- Byte-identical models verified on one environment only.
- The development benchmark has 43 benign rows from 12 senders.
- The model card's gate uses the test split, so passing it is not independent evidence.
